# TAW-67 memory investigation, 8 September 2026

**Sub-200 is a plausible engineering target for idle and ordinary reading. Sub-100 process RSS is not a realistic target for the current Linux stack. Neither is demonstrated by an optimized Tawaq build in this investigation.** A strict ceiling during streaming, source changes, and long reading sessions needs its own acceptance tests. The original approximately 400 MB observation was not reproduced at fresh startup.

This investigates [TAW-67](https://linear.app/tawaq/issue/TAW-67/reduce-release-build-ram-usage-from-roughly-400-mb). All measurements below use MiB, 1,048,576 bytes. A literal 200 MB decimal target is 190.7 MiB. RSS includes shared resident pages and excludes swapped pages; PSS apportions shared pages. Changing the metric does not constitute a reduction. See [Flutter's memory documentation](https://docs.flutter.dev/tools/devtools/memory).

The tested checkout was `4f741fdcf9131353967ab8494ba35225cb4db75b` plus the user's existing uncommitted audio, recitation, and settings work. Flutter was FVM 3.47.1, Linux x64, kernel 7.1.9-arch1-2, AMD Barcelo, amdgpu, Mesa 26.2.1, Hyprland/Wayland, Arabic, dark Manuscript theme. The resolved audio package was `mpv_audio_kit` 0.4.5, not the 0.4.2 lower bound in pubspec. Local package source and checked-out submodules were inspected.

## Measurements

The final release pass used a temporary entrypoint importing the real app, routing through its existing router and querying its existing repositories. A separate Python process sampled `/proc/PID/smaps`, `smaps_rollup`, and `status`. The entrypoint reported the mounted screen and image cache. This avoided the allocation noise found in the first experiment, which read the large smaps text inside Dart. The initial experiment's numbers are not used in this table.

| Sequential phase | RSS MiB | Process peak MiB |
|---|---:|---:|
| Prayer, 10 seconds after startup | 223.8 | 233.3 |
| Quran | 237.6 | 237.8 |
| Hadith | 230.4 | 242.1 |
| Muslim Fortress | 235.6 | 243.6 |
| Settings | 236.7 | 245.2 |
| Return to Prayer | 233.7 | 253.4 |
| Quran, eight page jumps | 239.3 | 253.4 |
| Open every translation, query 1:1 | 251.4 | 253.4 |
| Open every tafsir, query 1:1 | 260.3 | 260.3 |
| Ten seconds idle after database opens | 260.4 | 260.4 |
| Return to Prayer, ten seconds idle | 263.1 | 274.1 |

The compositor allocated the same 664×718 viewport at DPR 1 throughout this pass. Approximately 1.6 MiB was swapped, so the true footprint is slightly higher. Prayer PSS was 157.9 MiB initially and 197.4 MiB at the end, but those numbers depend on other processes sharing libraries. The installed, long-running app was initially only about 121 MiB RSS with another 45 MiB swapped; that was rejected as a fresh baseline.

A normal fresh release build without the temporary entrypoint was approximately 236 MiB RSS with zero swap in an earlier pass. The profile build started around 285 MiB RSS. Its main-isolate heap was 37.5 MiB after forced GC, with approximately 22 KiB reported external allocation. The class census contained substantial profile metadata such as Code, Function, and CodeSourceMap. Class census figures include different heap spaces and must not be summed as a replacement for RSS.

A minimal MaterialApp with a single text widget, the same project plugin registrant and asset declarations, and no Tawaq bootstrap measured **163.7 MiB RSS**, plus 3.2 MiB swap, at the same compositor window size. This is an observed control, not a universal Flutter minimum. It leaves little room for a complete app under 200 and is already well over 100.

## What owns the memory

The startup release mapping snapshot separates these resident allocations:

| Category | Approximate RSS MiB | Interpretation |
|---|---:|---|
| LLVM and Gallium graphics libraries | 59.9 | Present in the minimal control too; not Quran data |
| Dart heap mappings | 37.0 | Committed resident heap pages, not just live Dart objects |
| Native malloc heap and unnamed anonymous mappings | 46.6 | Mixed native allocations; cannot assign all of this to one package from smaps |
| App AOT library | 16.8 | Compiled code and read-only data |
| Flutter engine library | 12.0 | Engine code and data, separate from its heap allocations |
| Font mappings | 3.1 | Includes system fonts; not the entire font bundle |
| Remaining libraries, mappings, and shared buffers | About 48 | GTK, support libraries, audio, and other process overhead |

These categories explain why a dependency's archive or asset size is a poor RAM estimate. The root image cache reported zero bytes, zero entries, and zero live images throughout the sampled app flow. That excludes a large Flutter ImageCache as the cause in this flow; it does not measure engine raster caches or GPU allocations. Graphics-buffer accounting is separate and must not simply be added to RSS.

Font mappings were about 3.9 MiB after entering Quran and 4.7 MiB after the page-jump sequence. No QCF page fonts were resident at Prayer startup. Deleting the large Chinese font or hundreds of Quran fonts therefore does not offer a corresponding startup RAM saving. Font lifetime after a long session rendering many distinct pages remains unmeasured. The page-jump test is not proof that every requested page rasterized, so it is not a long-session font benchmark.

`mushaf_reader` already uses a LazyBox for 6,236 ayahs, defers its search box, and bounds its rendered-page model cache to 16–20 entries. The profile census showed 6,236 PageLayouts objects occupying about 0.29 MiB shallowly, about 0.77 MiB of Hive Frames, and about 0.58 MiB of Hive tree Nodes. Associated lists and strings add more, but these figures do not support blaming hundreds of megabytes on Quran records. Library initialization in `main.dart` and the global recitation transport nevertheless keep Quran infrastructure alive before the reader is opened.

## Strongest reduction opportunities

1. **Bound native audio buffering.** The app's audio configuration leaves mpv cache limits at their defaults. The actual bundled native library reported 150 MiB forward and 50 MiB backward limits, with a 1,000-hour time target. These are caps, not preallocated startup memory. A direct native test served an existing 26,197,050-byte recitation through localhost, kept playback paused, and used null audio output. With default limits, RSS rose from 21.4 to 91.1 MiB after loading. With an 8 MiB forward and 2 MiB backward cap, it rose from 21.5 to 35.8 MiB. That is approximately **55 MiB lower RSS** for this fixture, reproduced in two runs. The default demuxer retained about 58.5 MiB of packets from a 25 MiB compressed file; the bounded configuration retained about 8 MiB and 224.5 seconds ahead.

   This is dependency-level evidence, not a demonstrated 55 MiB saving in Tawaq. The app normally resolves saved recitations to local files; direct streaming occurs when persistence is disabled, and recovery paths also need inspection. Test uncached HTTP, offline files, partial-download recovery, seeks, repeats, pause/resume, and adhan interruption before choosing final limits. `Player.setDemuxer` and `Player.setCache` already expose the required controls, so an app policy change can be tried before changing the package. Package work could provide an audio-appropriate buffering preset without changing the global defaults for unrelated consumers.

2. **Stop loading full database assets just to validate an existing copy.** `AssetDatabaseService.openDatabase` loads the entire bundled database before comparing its size fingerprint to the sidecar, even when the disk copy is valid. Individual tafsir assets reach roughly 18 MiB. It also retains every opened SQLite handle until the service is disposed; the service is keepAlive. Opening all sources grew RSS by about 21 MiB relative to the preceding search phase in the final pass, mostly in native heap mappings. That delta includes asset loading, SQLite activity, and allocator behavior, and cannot all be labelled SQLite cache.

   Generate a small version/hash manifest so warm opens avoid reading the database asset. Retain the existing disk-copy compatibility and safe replacement behavior. Then measure a bounded connection cache with explicit ownership across AssetDatabaseService, TranslationRepository, and TafsirRepository. Closing handles only in the service would leave stale handles in repository maps. Query one ayah per source rather than loading corpora, as the current repositories already do. Relevant regression coverage starts at `test/core/database/asset_database_service_test.dart`.

3. **Measure native allocator retention before calling it a leak.** In the native audio test, `stop` cleared the path and demuxer state but RSS remained high. Even destruction could leave pages resident. A diagnostic `malloc_trim(0)` reduced the default run from 91.1 to 26.8 MiB. This establishes reusable allocator-held pages in that test; it does not establish leaked live audio objects. Prefer preventing the large buffer allocation. Do not add periodic trim calls to the app based only on this probe.

4. **Reduce the startup ownership cost, with modest expectations.** Trace `RecitationTransport` → recitation controller → audio service and Mushaf controller before making either lazy. Desktop alerts and media-session commands also use audio. Preserve session restoration and the first-play behavior. The minimal control's Dart mappings were about 5.8 MiB versus 37 MiB for Tawaq; its AOT mapping was about 4.4 versus 16.8 MiB. That identifies app-side headroom but does not make the entire difference removable. Theme construction, duplicate full theme variants, provider initialization, and the Prayer widget tree deserve allocation/retaining-path measurements before selecting a rewrite. A Forui replacement or a rewrite of the religious-content packages is not justified by this investigation.

5. **Treat Linux graphics cost as a platform constraint.** The same approximately 60 MiB of LLVM/Gallium RSS appeared in the minimal control. Changing `adhan_dart`, Dorar, or Quran storage will not remove those pages. A smaller renderer or native background-only companion might make sub-100 possible for a different process, but that is a product/architecture change and has not been benchmarked here. Hiding a window or waiting for swap is not evidence of meeting the budget.

## Search correctness finding

The research search calls returned zero results. Investigation found a concrete path collision: `MushafReaderLibrary.ensureInitialized(subDirectory: 'tawaq')` opens Quran boxes under Documents/tawaq. The app later calls `Hive.initFlutter()` for settings, changing the shared Hive default directory to Documents. When `ensureSearchIndexBoxOpen` eventually calls `Hive.openBox('search_index')` without an explicit path, it creates an empty Documents/search_index.hive.

In the copied test data, Documents/tawaq/search_index.hive contained 6,236 integer-keyed entries, including 48 values containing the tested الرحمن query. Documents/search_index.hive was zero bytes with zero entries. Both were inspected independently through Hive after the app stopped. The source agrees with these observed paths. No original user data was modified.

Fix the package's deferred open to use its owned `_hivePath`, and add a regression that initializes the Quran library, changes the application's Hive default directory, then searches. Check other delayed opens for the same ownership assumption. Do not remove lazy loading as a workaround. This correctness issue means the search sample is excluded as evidence of a successfully loaded search index or working search results.

## Scope, evidence, and next decision

I would authorize a sub-200 effort, beginning with audio limits and database asset validation, then measuring the startup owners. I would not promise a strict sub-200 ceiling across all flows yet, and I would not set sub-100 RSS as the release acceptance criterion for this desktop stack. If the target means proportional physical RAM instead, that is a different budget: this run was already around 158 MiB PSS at Prayer, but sharing and swap must still be recorded.

The work changed no production source or package. Existing uncommitted work was preserved. Fresh normal release/profile builds and temporary research builds succeeded. No production-code tests or full analysis were run because no implementation was changed. The normal release bundle was restored after the experiments. Test app processes and the localhost audio server were stopped; the installed user app was left alone. No Linear comment or issue update was posted.

App data was copied into `/tmp/taw67`; private D-Bus sessions prevented single-instance redirection. Those sessions had no desktop tray host, so tray integration and fully connected desktop services are a limitation. Viewport size was matched in the final pass, but native screenshots were unavailable through the GUI driver; mounted screens were verified through Flutter and routing. English layout, live network failures, full recitation sessions, a genuinely fresh first-install copy, and hours of distinct Quran-page rasterization were not validated. These remain implementation acceptance work, not demonstrated improvements.

The [evidence directory](taw-67-memory-2026-09-08/) contains external rollups, phase measurements, resident mapping totals, heap summaries, audio A/B output, and the temporary research scripts. The scripts preserve this machine's `/tmp/taw67` setup rather than pretending to be a general benchmark suite. Reproduction requires copied Documents and app-support data, an XDG user-dirs file pointing at those copies, the same FVM build and viewport, and separate D-Bus sessions. Build `study.dart` as a temporary release target, run it through `run_study.py`, and build the `STUDY_MODE=empty` variant separately for the control. Save the normal bundle before these builds and restore it afterward. `mpv_probe.py` uses only a localhost file server and the saved release library. Do not run the copied test setup against the original settings directory.
